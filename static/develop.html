Roka 网站开发

Roka 使用 TypeScript、Fastify 与 Socket.IO，前端主体为原生 JavaScript。本页面向新开发者，介绍项目结构、本地流程、检查、贡献与部署约定。仓库： https://github.com/oimasterkafuu/Roka

1. 贡献流程

  1. 外部贡献者 fork 仓库并 clone 自己的 fork；维护者从主仓库创建功能分支。
  2. 每个分支只处理一个主题，使用 feat/xxx、fix/xxx 等名称。
  3. 完成开发与验证后推送分支并创建 PR，说明动机、实现、影响范围和验证结果。
  4. 根据评审意见更新同一个分支，保持提交聚焦，不混入无关文件。

开始修改前请阅读仓库根目录的 AGENTS.md 与 MAP.md。维护者直接提交需要配置指定作者身份并启用 GPG 签名；外部贡献通过 PR 进行。

2. 环境要求

  • 建议使用 Node.js 22，与仓库工作流一致，并启用 Corepack。
  • 统一使用 pnpm，版本由 package.json 的 packageManager 锁定；不要使用 npm 或 yarn。 
corepack enable
pnpm install
pnpm run dev        # http://localhost:23333

3. 项目结构

src/           后端 TypeScript 源码
  server.ts      唯一入口：Fastify 路由与 Socket.IO 事件
  game-engine.ts 对局核心：Tick、战斗、连通、投降与回放
  game-engine/   常量、选点、榜单、编码、迷雾、回放与增兵模块
  map/           地图生成器与华夏地区配置
  server/        认证、验证码、房间、在线状态、托管与部署服务
  types.ts       共享类型与协议定义
  *-store.ts     用户、动态、公告与回放存储
static/        前端源码与静态素材
  index.html     首页与大厅
  game.html      对局与回放骨架，配合 main.js 和 main/
  styles/        页面样式，main.css 负责聚合
  intro/         介绍片运行时与独立构建产物
  develop*.html  网站开发指南与 bot 协议文档
bot-template/  四个 bot 参考实现
scripts/       测试、维护、迁移与观测脚本
data/          运行时数据，不入库
dist/          构建产物，不手工编辑

逐文件职责与修改定位见 MAP.md，本页不重复完整源码地图。

3.1 运行时数据

users.bin / feeds.bin 用户与动态数据，使用 v8 serialize 与 brotli；写入时保留 .bak 备份。
announcement.json 公告数据，原子写入并保留 .bak 备份。
server-bots.json 托管恢复状态：{ username, room, template, allowTeam, allowFog, allowMultiLine } 列表。
replays/ <id>.rpl 操作流、index.bin 索引与 <id>.rpb.gz 观看缓存。

4. 常用命令

命令以 package.json 的 scripts 为准。

pnpm run dev 用 tsx 启动开发服务器，默认端口 23333，并显式关闭静态 CDN。
pnpm run build 先独立构建介绍片及压缩资源，再用 tsc 编译 src/ 到 dist/。
pnpm start 运行 dist/server.js。
pnpm run lint ESLint 检查 src/**/*.ts；lint:fix 可自动修复。
pnpm run format Prettier 格式化 src/**/*.ts、static/**、README.md 与 AGENTS.md。
pnpm test 运行聚合回归套件；也可按需执行单项 test:*，部分测试需要先构建。
pnpm run test:bot 在临时数据目录启动服务，让两个 random-patch-bot 自动开局，验证基本接入与对局流程。
pnpm run observe:bot 录制 bot 对局并生成行为分析报告，用于策略维护。

5. 检查、提交与合并

提交前最小检查：
  • pnpm run lint、pnpm run build、pnpm run format 均通过。
  • 检查 git diff，不混入无关改动，并确认锁文件与依赖清单一致。
  • 运行方式、接口或配置变化时同步更新 README.md。
  • 文件结构、模块职责或协议变化时同步更新 MAP.md。
  • 合并到 main 的更新必须提升版本号：破坏性变更 major，新功能 minor，其余 patch。

5.1 提交信息

使用 Conventional Commits：<type>(<scope>): <subject>。subject 为英文祈使句，首字母小写且不超过 72 字符。常用类型包括 feat、fix、refactor、perf、docs、style、test、chore、ci 与 revert；破坏性变更需标注 BREAKING CHANGE:。

5.2 PR 合并工作流

bump-version-and-merge.yml 支持在 PR 下评论 OK. <major|minor|patch> [merge|squash|rebase]，或由维护者手动触发。工作流会升版、检查冲突并按指定策略合并；评论触发仅限指定维护者，且只支持同仓库分支。合并后自动删除的分支仅限 dev/ 前缀。

6. 部署机制

生产环境以 GitHub main 为准。push webhook 经 HMAC-SHA256 校验后触发：

git fetch origin main
git reset --hard origin/main
pnpm install --frozen-lockfile
pnpm run build
# systemd 环境退出并由守护进程重启，其他环境自行重启。
  • 有对局运行时先进入更新排队：广播状态、禁止开新局，最后一局结束后部署；默认 120 秒宽限到期时按当前名次清算残余对局。
  • 生产工作区中未推送的改动可能被自动部署覆盖，验证完成后应及时推送。
  • 重启期间 Service Worker 为导航请求显示 static/updating.html，服务恢复后自动返回。

7. 自动化

CodeQL 在 main 的 push、PR 与每周一定时任务中扫描 JavaScript/TypeScript，使用 build-mode: none；告警应及时处理。
Dependabot npm 生态每天检查，开放 PR 上限为 50。依赖 PR 逐个处理，合并时统一提升 patch 版本。
版本与合并 由第 5.2 节的工作流执行，不要把它当作覆盖所有测试的 CI。

8. 前端与静态资源

  • 前端主体是原生 JavaScript 与 jQuery，不经过统一前端打包；对局页脚本全局化且加载顺序敏感。
  • 普通静态文件由静态服务直接提供；全部 HTML 及 main.css、main.js、sw.js、sw-register.js 会替换 {{V}} 为当前版本号后发出。
  • 生产环境可把 JS、CSS、字体、图片与介绍片素材指向固定提交的 CDN，HTML、API 与 Socket.IO 仍由本站提供；开发命令默认使用同源资源。
  • 介绍片是独立构建入口，scripts/intro/build-intro.mjs 将 player-source.js 打包为 static/intro/player.js 并生成压缩资源，已包含在 pnpm run build 中。

9. 开发边界

  • 源码修改放在 src/ 与 static/，不要手工编辑 dist/；行为与源码不符时先重新构建。
  • 网站功能开发不要把 bot-template/ 当作服务端源码修改；需要调整 bot 时应单独验证对应模板。
  • Socket.IO 协议或格子编码变化要同步修改类型、服务端、前端消费方与 static/develop-bot.html。
  • tsconfig.json 刻意关闭 strict；改变严格度会影响整个后端编译面。
  • Prettier 使用单引号、分号、尾逗号与 110 列宽度，规则见仓库配置文件。
