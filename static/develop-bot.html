Roka 机器人开发协议

本文档是 Roka 对局协议的权威说明，每个事件名、字段与数值都与服务端实现（src/server.ts、 src/server/lobby-service.ts、src/game-engine/、src/types.ts）逐条核对。 人类和 AI 都可以直接照着写出一个可用的 bot。仓库： https://github.com/oimasterkafuu/Roka

1. 快速开始

仓库 bot-template/ 下内置四个参考实现（均为独立 pnpm 包，仅依赖 socket.io-client）：

random-patch-bot 协议最小参考（单文件 index.js）：进房、自动准备、周期心跳、维护本地全图缓存，每回合随机挑一个合法动作发送 attack。建议先把它跑通，再替换决策逻辑。仅 CLI，不可被服务端托管。
simple-strategy-bot 综合策略 bot（扩张/防卫/救援/进攻/经济/后勤/开局规划管线），strategy.js 导出 attachStrategy，CLI 与服务端托管共用同一份实现，用法见包内 USAGE.md。
anti-human-bot 独立重写的强对抗 bot（自带测试与离线训练体系），server-bot.js 导出 attachStrategy，可托管。
apex-bot 战术战役 bot（救城/拆建筑优先、滚动集结推进、迷宫专用策略），strategy.js 导出 attachStrategy，可托管。

1.1 获取 token

登录有图形验证码，bot 无法自动登录。先在浏览器登录，然后从开发者工具的 Cookie 中复制 auth_token 的值（即登录 JWT，有效期 7 天）。建议给 bot 单独注册账号，避免与浏览器互相顶号（见第 2 节单会话限制）。

1.2 环境变量（random-patch-bot / simple-strategy-bot）

BOT_SERVER 服务端地址，默认 http://127.0.0.1:23333。
BOT_ROOM 必填。要加入的房间号。
BOT_TOKEN 必填。上一步复制的 auth_token Cookie 值。
BOT_TEAM 组队模式下的目标队伍号，默认 1；非组队模式会被服务端规整为参赛。
BOT_AUTO_READY 默认 1（自动参赛并准备）；设为 0 关闭。
BOT_ACTION_DELAY_MS 每回合决策后的发送延迟毫秒数，默认 120（apex-bot 默认 0，收到最新帧即决策）。 
cd bot-template/random-patch-bot
pnpm install
BOT_SERVER=http://127.0.0.1:23333 BOT_ROOM=your-room BOT_TOKEN=your-auth-token pnpm start

anti-human-bot 的环境变量集合略有不同：无 BOT_TEAM / BOT_ACTION_DELAY_MS，另有 BOT_PARAMS（策略参数 JSON），且默认连接生产服务器 https://roka.oim.moe:444/、默认房间 bot；详见其 USAGE.md。

1.3 由管理员在服务端托管运行

超级管理员可以在后台管理页 /admin 的「策略 Bot」分区直接启动可托管模板（ simple-strategy-bot、anti-human-bot、apex-bot 会被自动枚举，random-patch-bot 不在其列）：只需提供已注册用户名与房间号，服务端在本进程内用内存临时令牌连接自身 socket 完成登录，无需验证码与 token。托管规则的完整说明见第 7 节。

2. 连接与鉴权

Socket 地址 与站点同源，Socket.IO 默认路径 /socket.io/。
transport 服务端仅允许 websocket 与 polling。
鉴权优先级 握手中间件依次尝试：1) auth.token 命中 ROKA_BOT_TOKENS 表；2) auth.token 命中服务端托管 bot 内存令牌；3) 按 JWT 校验（优先 auth.token，缺省时回退握手 Cookie 里的 auth_token）。JWT 除签名外还校验会话有效性：重新登录会轮换 session 使旧令牌失效。
Bot 专用令牌 服务端可用环境变量 ROKA_BOT_TOKENS（格式 "token1:username1,token2:username2"，用户名须匹配 [A-Za-z0-9_]{3,20}）配置合成 bot 账号：握手 auth.token 命中表项时直接以对应用户名放行，无需注册。
鉴权失败 连接被拒绝，客户端收到 connect_error（消息如「未登录或登录已失效。」；已封禁账号收到封禁文案）。例外：带 ?home=1 的连接匿名放行，仅接收首页全局广播，收不到 set_id。
身份标识 set_id 连接后服务器下发 set_id（字符串），值为当前 socket id 的 MD5。后续在 room_update.players[].sid、init_map.player_ids 与 update.kills 中都用这个 ID 标识自己。
单会话限制 同一用户名同时只允许一个 socket：新连接成功后，该账号的旧连接会被服务端直接断开（顶号，旧连接只收到底层 disconnect，无业务事件）。例外：bot 连接（ROKA_BOT_TOKENS 合成账号与服务端托管 bot）不参与顶号互斥，不会顶掉同名的浏览器连接，也不会被顶掉。
断线宽限与换绑 对局中掉线（含被顶号）有 10 秒宽限期：期间不判挂机、不投降，操作队列继续执行。10 秒内重新连接并对同一房间发送 join_game_room 即可恢复对局：服务端把该玩家的 socket 换绑到新连接，清空其操作队列，并补发 init_map 与一帧全量 update（注意此时 init_map.player_ids 与 update.kills 中的自己 ID 已变为新 set_id）。超过宽限期以「挂机」原因自动投降并转为观战。换绑按用户名匹配且只在同类连接之间进行（bot 连接只能接管 bot 的旧席位、浏览器连接只能接管浏览器的旧席位）：同名人类玩家在对局中打开房间页不会抢走 bot 的席位，而是作为新成员进房观战。 
// JS 连接示例（socket.io-client）
const { io } = require('socket.io-client');
const socket = io(BOT_SERVER, {
  transports: ['websocket', 'polling'],
  auth: { token: BOT_TOKEN }
});
socket.on('set_id', (id) => { /* 保存为自己的 client id */ });

3. 房间阶段协议（开局前）

3.1 Client → Server

join_game_room { room: string }。房间号仅限制长度 1..15，无字符集限制；不合法时静默忽略。先尝试断线换绑（见第 2 节），否则正常进房；本连接已在其他房间时重复发送会被忽略。房主为房间成员列表首位：服务端托管 bot 进房时固定排在普通成员之后，房主位置保留给第一个人类用户或第三方 bot。对局进行中进房自动成为观战者，补发 init_map（general: [-1, -1]）与一帧全量 update。
change_team { team: number }。合法范围 0..16：0 表示观战（同时强制取消准备）；1..16 表示参赛/队伍号。非组队模式下，非 0 会被规整为 1（参赛）。参赛者满 16 人时从观战转参赛会被拒绝。对局进行中仅观战者与已战败玩家可换队（决定下一局的「观战/参与」模式），存活参赛者需等对局结束。
change_ready { ready: boolean }。仅参赛者有效（观战席恒为未准备），且仅在房间未开局时生效；部署更新排队期间会被拒绝并收到提示消息。
change_game_conf 可选字段 patch，仅房主可改，对局进行中不生效。合法字段： speed（0.5~4 浮点）、allow_team（bool）、fog（bool，迷雾远征）、map_size（normal|large，其余值归一为 normal）、map_mode（random|maze|archipelago|mediterranean|huaxia，未知值归一为 random）、map_region（华夏模式地区：qin|han|tang|liao|song|yuan|ming|china|taiwan；别名 three-kingdoms、northern-dynasties 归一为 han，旧值 qing / hong-kong 归一为 china，其他未知值和缺省值回退为 china）、map_token（trim 后最长 32；非空输入视为自定义种子， 对局结束后沿用不重随机，清空则恢复每局随机）。华夏系列仅在每年中国时区（Asia/Shanghai）10 月 1 日至 10 月 7 日（含全天）开放；非活动期设置请求会被拒绝（房间消息提示），过期房间配置在 room_update 与开局时回退为 random（配置本体不改）。回放重建不受当前日期影响。 房间内存在不允许组队的服务端托管策略 Bot 时不允许组队：allow_team 开启请求会被拒绝（房间消息提示），且托管 Bot 进房时会强制关闭已开启的组队模式；允许组队的托管 Bot 则由房主自由开关组队。同理，房间内存在第三方 Bot 或未允许迷雾的托管 Bot 时不允许开启 fog，这类 Bot 进房时会强制关闭已开启的迷雾。
room_heartbeat {}（网页端附带 { visible, focused }，服务端不解析字段）。房间页每 30 秒上报一次，证明标签页仍然开启。仅在房间准备阶段检查：超过 600 秒未收到心跳，或在房停留累计超过 12 小时（即使心跳正常）的成员会被服务端自动移出房间（收到 room_kick）。对局进行中不检查（对局断线走 10 秒宽限期机制，停留超限也等本局结束后再移出）。所有 bot 连接（ROKA_BOT_TOKENS 与服务端托管 bot）豁免心跳与停留检查；使用普通用户 JWT 的 bot 需自行周期发送心跳。

3.2 Server → Client

room_update 房间状态快照： { speed, allow_team, fog, map_size, map_token, map_token_custom, map_mode, map_region, in_game, update_queued, players, ready, need }。fog=true 表示本房间开启了迷雾远征；map_token_custom=true 表示当前种子为房主自定义（对局结束后沿用不重随机）；map_mode/map_region 均为归一化后的值。update_queued=true 表示部署更新排队中：禁止开新局（ change_ready 会被拒绝并收到提示消息），宽限期（默认 120 秒）内未结束的对局将按当前名次清算。
room_update.players[] 每项为 { sid, uid, team, ready, server_bot?, server_bot_allow_team?, server_bot_allow_fog?, bot? }： sid 为该玩家 socket id 的 MD5；uid 为用户名；team 为 0（观战）或队伍号；ready 为准备状态（观战席恒为 false）； server_bot 仅在服务端托管策略 Bot 成员上为 true； server_bot_allow_team / server_bot_allow_fog 仅在 server_bot 为 true 时下发，表示该 Bot 是否允许组队/迷雾； bot 在任意 Bot 成员（含第三方 Bot）上为 true。
ready / need 当前已准备人数 / 开局所需人数。need = floor(参赛人数 / 2) + 1（参赛者少于 2 人时为 0）。ready >= need 且 need > 0 即自动开局（简单多数）；need <= 1 时不会开局。组队模式下若所有参赛者处于同一队伍，服务端拒绝开局并提示调整队伍。
starting {}。满足开局条件后广播，表示即将进入对局；约 2 秒后首帧，随后收到 init_map。
chat_message 聊天消息：{ sender, color, text, team }。系统消息 sender 为空、 color=0；跨房间转发的非队伍消息额外带 room（来源房间号）。
room_kick {}。因心跳超时（准备阶段 600 秒无 room_heartbeat）或在房停留超过 12 小时被服务端移出房间；网页端收到后跳转回首页。被移出后连接仍然保留，可重新 join_game_room。
deploy_queued { queued }。部署更新排队状态全局广播（所有连接，含首页）：queued=true 表示进入排队（网页端对局中显示「系统即将更新」横幅、禁用开始按钮）；false 表示更新未重启而结束（失败或演练），排队状态解除。排队状态解除后服务端不主动重开对局，bot 需照常重新准备触发开局。
left {}。return_room / leave 的确认回执。
提示：房间内只剩 bot（所有剩余成员 bot=true，观战的人类除外）时，服务端会在准备阶段把房间设置整体重置为默认值（speed 1、不组队、无迷雾、随机新种子、map_mode=random、map_size=normal）并提示；对局进行中不触发，等本局结束后才重置。

4. 对局阶段协议（开局后）

4.1 开局事件 init_map

n / m 地图行数 / 列数。格子下标 idx = x * m + y（行优先）。
player_ids 所有玩家的 MD5 SID 数组。用 set_id 在其中查找下标（从 0 开始），你的 owner id = index + 1；查不到即为观战。
general [x, y]，你自己的主城坐标；观战者为 [-1, -1]。

4.2 回合事件 update

整体结构 { grid_type, army_cnt, isolated, fog?, lst_move, leaderboard, turn, kills, game_end, is_diff, replay? }
turn Tick 计数（前端显示为 Math.floor(turn/2) 回合）。1 Tick = 0.5 秒（速度 1x），实际间隔为 500 / speed 毫秒，speed 0.5~4 只缩放 Tick 间隔。奇数 Tick 各队操作执行顺序反转（后手补偿）。
is_diff = false 全量帧：grid_type、army_cnt、isolated 都是长度 n*m 的全量数组，按行优先展开。下发时机：开局/进房/重连补发、每 50 Tick 定期、每 Tick 约 1/51 概率随机补发、终局帧；观战者每 Tick 都收全量帧。
is_diff = true 差分帧：grid_type/army_cnt/isolated 均为 index-value 对： [idx0, val0, idx1, val1, ...]。机器人需要在本地缓存全图并增量合并（isolated 在差分帧中可能为空数组，表示本帧无孤军状态变化）。
isolated 取值 0 正常；1 断链宽限期（断链后前 10 Tick，只闪烁、尚未衰减）；2 衰减期（第 11 Tick 起每 2 Tick 衰减一次，公式见 5.3）。
fog 可选数组，仅房间开启「迷雾远征」的实时对局下发（回放与默认观战不含视野过滤）：长度 n*m（差分帧同样为 index-value 对），1 表示该格在己方队伍视野外，0 表示可见（全视野接收者在迷雾对局中收到全 0 数组）。过滤规则见 5.4。
lst_move { x, y, dx, dy, half, mode, op, skip }。表示服务器本 Tick 为你执行的最近操作（用于客户端队列确认）。op：'m' 推兵、'b' 建成指挥所、'c' 升级主城（后两者 dx=dy=-1）。本 Tick 无执行时为 { x:-1, y:-1, dx:-1, dy:-1, half:false, mode:0, op:'m' }。 skip 为本 Tick 被执行操作之前因条件不满足被自动丢弃的队首操作数（无执行时为本 Tick 全部丢弃数）；失效操作会被服务器直接移出队列，后续操作在同一 Tick 继续尝试执行。观战者收到的是占位值（全 -1，skip=0）。
leaderboard[] 每项结构：{ team, uid, army, land, class_, dead, id }。army 为全图兵力合计，land 为格数，id 为座位号（1 起），dead 为出局次序（0 = 存活）。class_ 可为 '' 或 'dead'（ 'afk' 是历史遗留取值，当前版本不会出现）。仅参赛者入榜。
kills Record<sid_md5, killer_name>。当你被击败时，键为你的 set_id。值为击杀者用户名；无攻击者的系统接管为 '系统'，投降/挂机路径为 '投降' / '挂机'。
game_end true 表示该帧为终局帧（终局帧必为全量帧）。
replay 可选字符串，仅在终局帧出现，表示回放 ID（/replays/<id> 可观看）。

4.3 格子编码（grid_type 线上编码）

0..49 普通地块，owner id = code（0 表示无兵中立，极少出现；中立空地一般为 200）。服务端内部记为 0。
50..99 指挥所，owner id = code - 50（内部 -1）。只能由玩家建造（build 操作，相当于 X 键，消耗 50 兵），地图不再预置；与普通地块一样每 50 Tick +1 兵（不享受爆发期加成），是连通锚点。
100..149 主城（将军），owner id = code - 100（内部 -2）。每 Tick +1 兵；失去所有主城即出局。
150..199 己方沼泽，owner id = code - 150（内部 2）。不产兵、不可建造，但参与连通。
200 可见空地（中立）。
201 可见山脉（内部 1），不可通行、不可被推兵选中。迷雾对局中视野外山脉仍保持为 201。
202 / 203 / 205 （已废弃）旧版迷雾编码。现已无此类状态，服务器不会下发。
204 可见中立沼泽。迷雾对局中视野外沼泽（含敌方沼泽）统一抹成 204（隐藏归属）。

army_cnt 与 grid_type 同维度。默认无迷雾远征：update 始终携带全图真实状态（全图可见）；房间开启「迷雾远征」时改为按视野过滤（见 5.4）。

5. 规则要点

5.1 增兵规则

主城 每 Tick +1 兵（无主城即出局，故恒为正常领土）。
普通地块 / 指挥所 turn % 50 == 0 时 +1（即第 50、100、… Tick），孤军不产兵；指挥所不享受爆发期加成。
爆发期 第 26~50 Tick（闭区间）：正常普通领土每 Tick 额外 +1（与 50 整除可叠加，第 50 Tick 当 Tick +2）。
沼泽 / 中立格 永不产兵。兵力无上限。

5.2 战斗结算

  • 攻击兵力必须严格大于防守兵力才能占领；未严格大于（含相等）时进攻失败但双方互损：进攻方损失全部推出兵力，防守方等量扣除（最低到 0，归属与建筑不变）。
  • 占领有损耗：占领成功后目标格新兵力 = 攻击兵力 − 守军兵力；被占领的指挥所/主城会被摧毁（降级为普通地块）。
  • 攻下敌方最后一座主城 → 该玩家出局，残余领土不再转移给攻击方：锚点全部拆除为普通地块、兵力按断链规则减半（⌊n/2⌋，1 兵保持为 1，减半后归零直接变中立），随后全部沦为孤军并按孤军规则逐渐衰减至中立。

5.3 连通与孤军

连通按队伍计算：经由连续的本队存活成员格子四方向连通到队内任意存活成员的主城/指挥所即为正常领土（只要队伍在这一块里还握有任意一座主城/指挥所，全队的这块领土都可操控）；否则成为孤军（见 update.isolated）：

断链瞬间：兵力减半 n' = floor(n / 2) （n = 1 时保持 1；减半后 ≤ 0 直接变中立） 宽限期： 断链后前 10 Tick 只闪烁（isolated = 1），不衰减 衰减期： 第 11 Tick 起每 2 Tick 衰减 max(1, ceil(n × 5%)) （isolated = 2，归零变中立、建筑拆除） 重连： 恢复正常且兵力 ×2

孤军格子不可推兵、不可建造（校验直接失败）。被切断的领土会持续衰减，扩张时务必保持连通。

5.4 迷雾远征（fog-vision）

房间可开关（默认关闭）。开启后，存活参赛者只收到己方队伍视野内的真实状态；观战者、已出局者与回放始终全视野。

视野范围：己方（含队友）任意格子为中心、切比雪夫距离 ≤ 1 的全部格子 即 visible(idx) = ∃ 己方格 (x, y): max(|x' - x|, |y' - y|) ≤ 1
  • 视野外格子：grid_type 中山脉保持 201，沼泽（含敌方沼泽）统一抹成 204，其余一切（敌方领地、指挥所、主城、中立城市、空地）一律抹成 200； army_cnt 与 isolated 均为 0，并附 fog 标记——视野外的真实地形、归属与兵力都不会下发。
  • 视野内一切照常下发：地形、归属与兵力完整，包含敌队指挥所（owner+50）、敌队主城（owner+100）与中立城市（50）。
  • 观战者可用 spectate_view 切换到某支队伍的视角（见 6.7）。

5.5 投降、挂机与终局

  • 投降 = 立即放弃所有控制权：若队内仍有其他存活成员，全部领土（含兵力）转移给编号最小的存活队友，主城降级为指挥所；否则主城与所有指挥所拆除为普通空地，领土兵力减半后沦为孤军进入自然衰减。投降后转为观战。
  • 挂机判定：自最后一次成功执行操作起，闲置满 60 Tick 且满 60 秒（两者同时满足）自动以「挂机」投降；断线超过 10 秒宽限期同样以「挂机」投降。
  • 存活队伍数 ≤ 1 时对局结束：广播 game_end=true 全量终局帧（携带 replay 回放 ID），随后结算 rating。部署更新排队宽限到期时，残余对局按当前排行榜名次强制清算（同样产出终局帧与回放）。
  • 回放为 ops-v1 操作流，观看时由引擎整场重建；回放帧恒为全视野，不含 fog 字段，bot 无需消费回放协议。

6. 对局内可发送操作

6.1 attack（推兵）

payload { x, y, dx, dy, mode, half }。坐标均为 [row, col]。(x,y) 是起点，(dx,dy) 是目标，要求四邻接（|x-dx| + |y-dy| = 1）。入队时只解析字段不校验局面；执行时校验：起点归己方、非孤军、兵力 > 0、目标不是山。
mode = 2 全冲 推出 A - 1（A 为起点兵力，只留 1 兵看守）。对应普通点击 / WASD 之外的「全力」操作。
mode = 1 半兵 先按智能分兵算出理论推出量，再减半取整（一次性）。对应 Z 键。
mode = 0 智能分兵 为其他三个方向的「非山脉且非本队」相邻格保留驻军后推出余量。对应 Shift。公式（A = 起点兵力）：
half 兼容回退 仅当 mode 缺失或不是 0/1/2 时：half=true 回退为 mode=1，否则按 mode=0 处理。有效的 mode 始终优先。注意：不显式传 mode 且 half 缺省/false 时是智能分兵而非全冲；要全冲请显式传 mode: 2。
队友主城累兵与转属 有效推兵进入存活队友主城时会累兵；若该队友执行当刻拥有至少两座主城，目标主城还会自动转属出兵玩家（保持建筑及后续产兵），最后一座只累兵不转属。空推兵或点击不能转属，无需额外事件（旧版显式转让入口已移除，仅存回放兼容）。
mode 0 / 1 推兵量： B = Σ 其余三方向相邻格中「非山脉且非本队」格子的 (兵力 - 1) push = max(0, A - B - 1) mode = 1 时 push = floor(push / 2) 最终推出 min(push, A - 1)；推出 0 兵为无效操作 
// 从 (3,4) 向 (3,5) 全冲
socket.emit('attack', { x: 3, y: 4, dx: 3, dy: 5, mode: 2 });

6.2 build（建造）

{ x, y, op }。op='b' 建造指挥所（相当于 X 键），op='c' 升级主城（相当于 C 键），均消耗 50 兵；其他 op 值直接被忽略。与 attack 共用同一队列，每 Tick 每玩家最多执行一条队列操作，队列长度无上限。服务端入队只记录合法的 op 与坐标，不校验地形、归属、兵力或连通，可排在队列很靠后的未来位置；执行时才校验（指挥所须建在己方普通地块、主城须由己方指挥所升级、兵力 ≥ 50、非孤军），条件不满足会自动跳过（通过 lst_move.skip 告知丢弃数量），不会产生消耗。在普通地块上连发 b + c 两条即可两 Tick 后建成主城（相当于在普通地块按 C 键）。

6.3 队列管理

clear_queue 清空当前玩家待执行操作队列（Q 键）。
pop_queue 删除队尾一条待执行操作（E 键）。

6.4 send_message

{ text, team }。team=true 表示队伍频道（仅同队成员可见）；否则房间广播。空白文本被忽略。

6.5 surrender

投降并转观战：立即放弃所有控制权（规则见 5.5）。注意：24 小时内 20 回合内手动投降满 3 次会触发自动封禁（见 7.3），bot 应避免快速投降策略。

6.6 return_room / leave

退出对局返回房间（对局中按离开投降处理）。服务端会回 left。

6.7 spectate_view（观战视角）

仅迷雾对局的观战者可用；存活参赛者请求被忽略。{ team }：team > 0 且该队伍存在时，改按该队伍的可见性下发迷雾帧（与该队伍玩家所见一致）；team <= 0 恢复全图。切换后服务端立即补发一帧全量帧（并对齐 diff 基线）。

7. 服务端托管 Bot 与运行限制

7.1 托管机制

  • 仅超级管理员可操作：GET /api/admin/bots、GET /api/admin/bot-templates、 POST /api/admin/bots/start（{ username, room, template, allowTeam, allowFog }）、 POST /api/admin/bots/stop。
  • 模板自动枚举：bot-template/ 一级子目录中存在 strategy.js 或 server-bot.js 且导出 attachStrategy 的即为可托管模板（模板 ID = 目录名，展示名/描述取自其 package.json）。random-patch-bot 没有该入口，不可托管。
  • 启动校验：用户存在且未封禁、房间号长度 1~15、模板可托管；同一用户名或同一房间已有托管 bot 时冲突（HTTP 409）。
  • 不另起进程：每次启动生成随机内存令牌（stop 即失效），在服务器进程内用 socket.io-client 连本机回环地址完成正常握手；服务端固定向策略传 { room, team: 1, autoReady: true, log }（anti-human-bot 有意忽略 team 参数、固定首选 2 队并自主避让人类队伍）。
  • 重启自动恢复：运行中 bot 的 { username, room, template, allowTeam, allowFog } 列表原子写入 data/server-bots.json；服务重启后逐条重新校验并按原配置自动启动，失效记录记警告跳过并清除。

7.2 托管 Bot 的特权与约束

  • 不参与单会话顶号互斥；豁免房间心跳与 12 小时停留踢出。
  • 进房时固定排在普通成员之后，永远不会成为房主（房主保留给人类用户或第三方 bot）；bot 单独在房时暂居首位，任何普通成员进房即接任房主。
  • allowTeam=false 的托管 bot 进房会强制关闭组队模式，房主开启组队的请求也会被拒绝； 未允许迷雾的 bot（含第三方 bot）同理强制关闭迷雾。
  • 对局结束后的自动重新准备是策略自己的行为（由后续 room_update 驱动），不是管理器保证；编写可托管策略时应实现这一点。

7.3 自动封禁策略（对 bot 账号同样适用）

快速投降 20 回合内手动投降计一次 rapid_surrender；24 小时内满 3 次触发自动封禁。
挂机 挂机（afk）判负计一次；24 小时内满 6 次触发自动封禁。纯 1v1 对局的 afk 不计；主动离开（leave）与断线超时不计入任何计数。
封禁时长 基础 1 小时，按历史自动封禁次数翻倍（60 分钟 × 2^n），封顶 7 天；连续 14 天无违规则计数重置。

8. 增量帧合并示例

// 已知 n, m 和本地 fullGrid/fullArmy/fullIsolated（长度 n*m）
function applyDiff(pairs, target) {
  if (!Array.isArray(pairs)) return;
  for (let i = 0; i + 1 < pairs.length; i += 2) {
    target[pairs[i]] = pairs[i + 1];
  }
}

function applyUpdate(frame) {
  if (frame.is_diff) {
    applyDiff(frame.grid_type, fullGrid);
    applyDiff(frame.army_cnt, fullArmy);
    if (frame.isolated) applyDiff(frame.isolated, fullIsolated);
    if (frame.fog) applyDiff(frame.fog, fullFog);
  } else {
    fullGrid = frame.grid_type.slice();
    fullArmy = frame.army_cnt.slice();
    fullIsolated = (frame.isolated || new Array(n * m).fill(0)).slice();
    if (frame.fog) fullFog = frame.fog.slice();
  }
}
提示：
  • 任何时刻都维护一份全量缓存，避免只依赖 diff 帧。
  • 收到 is_diff=false 全量帧时，用它重置本地状态（每 50 Tick 必有一帧，另有随机补发）。
  • 断线重连后本地队列已被服务端清空，且自己 ID 变为新 set_id，需同步重置。

9. 常见坑

  • 单会话顶号：同一用户名新连接会顶掉旧连接。用普通用户 JWT 的 bot 与浏览器同账号并存时会互相挤掉，建议给 bot 单独注册账号（或使用服务端 ROKA_BOT_TOKENS 合成账号）。
  • 队列节流：每 Tick 每名玩家最多执行一条队列操作。一帧内连发多条 attack/build 只是入队，不会立刻全部生效；规划节奏时按 Tick 计算。
  • 推兵模式优先级：按键上 Shift（智能分兵，mode=0）> Z（半兵，mode=1）> 普通（全冲，mode=2）。不显式传 mode 且 half=false（或省略）时，服务端按 mode=0 智能分兵处理——旧式 { x, y, dx, dy, half: false } 并不等于全冲；要全冲请显式传 mode: 2。
  • 操作确认：服务端不回 ACK，用 update.lst_move 对照本地队列：skip 条队首操作被丢弃后，本 Tick 执行的那一条与 lst_move 匹配。
  • 孤军不可操作：isolated != 0 的格子不可推兵、不可建造，推兵校验会直接失败。
  • 山脉不可通行：推兵目标为山（201）时校验失败；迷雾对局中视野外的「空地」可能是任何地形，向视野外推兵照样按真实地形校验。
